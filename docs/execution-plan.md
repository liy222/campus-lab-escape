## 二 游戏内容和可复现通关路线

主题为虚构校园实验室。夜间断电后，玩家需要找到门卡、恢复设备电源、完成出口检查。目标是在10至15分钟左右完成一次试玩；时间仅作为体验目标，最终由真实试玩调整。所有文字和道具自编，不涉及真实危险操作。

| 房间 | 线索与动作 | 状态与后续 |
| --- | --- | --- |
| R1 值班室 | 值班便签含三角3、圆8、方2；柜门顺序为三角、圆、方。查看后输入382，打开柜子，拾取门卡。 | 门卡在背包才可首次解锁R2；柜子开后可查看内容。 |
| R2 设备间 | 拾取桌上保险丝并安装到电源箱；通电后屏幕显示青7、橙2、紫4，抽屉标签给出顺序。输入724并拾取应急钥匙。 | power_on为真；钥匙在背包可解锁R3，基线保留钥匙。 |
| R3 出口控制室 | 检查单要求冷却、通风、照明；标签分别对应2、3、1。输入231完成出口检查。 | power_on与check_done都为真且玩家在R3，才可移动至EXIT并获胜。 |

### 标准手动路线

新游戏 → 查看值班便签与柜门标签 → 输入382 → 拾取门卡 → 用门卡解锁R2 → 移动至R2 → 拾取保险丝 → 安装到电源箱 → 查看通电屏幕与抽屉标签 → 输入724 → 拾取应急钥匙 → 解锁并进入R3 → 查看检查单和设备标签 → 输入231 → 前往出口 → 通关。

### 对象设计约定

建议固定对象ID为r1_note、r1_cabinet、r1_door、r2_fuse、r2_powerbox、r2_monitor、r2_drawer、r2_door、r3_checklist、r3_panel、exit_door；道具ID为access_card、fuse、emergency_key。规格Agent可调整命名，冻结后前后端和测试统一使用。

线索正文只有inspect对应对象后才进入已发现线索。柜内门卡、抽屉内钥匙只在容器打开后可见；未通电的屏幕只返回“当前无显示”。秘密答案与完整解法保存在服务端及离线判定资料，前端公共配置不得含答案或隐藏条件。

### 负向体验

错误密码返回可理解的错误并保持状态；缺少道具说明缺口；未开门不能跳转；重复拾取不增加第二件道具；通关后停止推进并提供重新开始。玩家可随时手动操作，AI故障不影响已完成状态。

## 四 软件结构和目录边界

浏览器负责显示与收集输入；FastAPI负责规则、会话、存档和AI控制；SQLite保存可信状态与事件。模型只提出受限工具请求或解释，不承担真值判断，也不直接连接数据库。课程实验和评价入口独立于游戏页面。

| 模块 | 建议路径 | 职责 |
| --- | --- | --- |
| 前端 | frontend/src/ | Scene、Inventory、Clues、Assistant、ConfirmDialog、GameResult、API客户端。 |
| 规则服务 | backend/app/domain/ | 状态类型、可见投影、规则分发、房间与道具配置。 |
| 接口与存储 | backend/app/api/ 与 storage/ | 会话鉴权、事务、幂等、存档和提案存储。 |
| AI层 | backend/app/ai/ | Provider适配器、上下文构建、工具Schema、调用限制、提案生成。 |
| 验证 | tests/unit/、tests/api/、tests/e2e/ | 规则与API断言、界面流程、异常和回归。 |
| 实验 | experiments/ | 冻结样本、ground_truth、两种上下文、逐次调用及汇总。 |
| 评价器 | evaluation/ | 可信rubric、受限读取、预检、LLM判读、输出校验与校准。 |
| 工程材料 | docs/、evidence/、release/、scripts/ | 规格、决定、任务卡、原始事实、交付索引与运行入口。 |

### 可见投影与秘密配置

GameState内部包含room_id、inventory、discovered_clue_ids、flags、opened_containers、status、revision和generation。visible_state只返回当前可见对象、已发现线索、背包和公开反馈，不返回密码答案、未发现文本或完整规则表。HTTP响应与AI上下文统一调用该投影，避免两个出口使用不同过滤规则。

### SQLite最小数据表

sessions保存会话与当前状态；events追加动作及结果；action_receipts保存request_id与请求摘要；proposals保存一次性确认动作；saves保存单槽快照。密码答案作为受控关卡配置加载，不在API序列化。API层不得绕过domain直接写flags。

各状态修改在事务内读取、校验、更新并记录结果；单机SQLite足够首版。无需消息队列、微服务或复杂ORM平台。导出证据不含密钥及会话能力令牌；内容哈希用于检测意外损坏，不能替代访问授权或真实性证明。

## 五 HTTP接口和六个工具契约

下表是拟定接口契约，T02冻结字段与错误码后才能并行实现。匿名游戏会话使用服务端生成的高熵能力令牌，浏览器保存于sessionStorage；涉及该会话的接口校验X-Session-Token。无账户系统，但会话间仍隔离。

| 接口 | 输入与输出 | 规则 |
| --- | --- | --- |
| POST /api/sessions | 创建会话；返回session_id、token、visible_state。 | 只有创建响应返回token，不写入普通Trace。 |
| GET /api/sessions/{id}/state | 带会话token；返回可见投影。 | 不包含隐藏配置或模型凭据。 |
| POST /api/sessions/{id}/actions | request_id、revision、generation、tool、arguments；返回结果与新状态。 | 用于玩家手动动作；AI运行时不暴露该HTTP能力。 |
| POST /api/sessions/{id}/ai/turns | 用户问题、当前版本；返回answer、clue_refs和至多一个proposal。 | 只读工具可在预算内执行；改变进度的工具只生成提案。 |
| POST /api/sessions/{id}/proposals/{pid}/confirm | 会话token及提案标识；返回原动作的真实结果。 | 服务端加载保存参数，客户端不能改写确认动作。 |
| POST .../proposals/{pid}/cancel | 会话token；返回取消状态。 | 取消不执行游戏动作。 |
| POST .../save 和 .../restore | 保存或恢复该会话单槽状态。 | 校验归属、关卡和Schema版本；恢复失效旧提案。 |

| 工具 | 参数 | 前置与效果 |
| --- | --- | --- |
| inspect | object_id | 对象必须当前可见；返回描述，必要时登记发现线索。 |
| get_inventory | 无 | 返回已持有道具，不改变进度。 |
| take | item_id | 道具可见且未领取；加入背包，不能重复增加。 |
| use_item | item_id、target_id | 道具与目标合法且满足前置；开门或装保险丝。 |
| submit_code | target_id、code | 只接受有限长度字符串；规则判断，不显示正确答案。 |
| move | destination_id | 只可去相邻且已解锁房间；出口还需全部通关条件。 |

工具参数用Schema校验，禁止额外字段；对象与目标再做动态可见性和业务检查。HTTP错误建议统一为BAD_ARGUMENT、NOT_VISIBLE、PRECONDITION_FAILED、STALE_STATE、PROPOSAL_EXPIRED、FORBIDDEN_SESSION、MODEL_UNAVAILABLE。错误也返回可追踪event_id。

## 六 状态不变量和确认事务

### 必须持续成立的规则

门未解锁不能移动；物品只能在可见且未领取时进入背包；未供电不能读取屏幕线索；完成状态只能由合法出口动作产生；失败请求不改变游戏进度。客户端发送won或flags字段一律拒绝，不能把前端隐藏按钮当成后端校验。

### revision与generation

每次改变可信状态后revision递增；发现新线索也计为状态变化。新游戏、重置及恢复生成新的generation。restore只恢复玩法字段，当前revision继续递增，不回退事件编号；旧快照和旧提案携带的generation不再有效。AI完成所有只读探索后，用最终版本生成提案。

### 确认过程

1 AI工具分发器收到进度动作，校验名称、参数和当前前置条件，只写proposals。保存proposal_id、会话、动作、参数摘要、revision、generation、过期时间和status=pending。建议默认120秒过期。

2 前端显示将执行的实际动作、引用线索和确认或取消。确认端点只接受已保存提案标识，不接受替换后的code、target或item参数。

3 后端在事务中重新校验归属、pending状态、期限、版本及前置条件；执行一次规则转换，更新状态和日志，将提案标为committed。对同一提案重复确认返回已记录结果，不重复执行。

4 取消、过期、版本冲突或前置不满足时不执行。前端移除过期按钮，提示重新请求建议。模型对真实结果的解释在执行完成后生成，不能先宣告成功。

### 幂等和同时操作

先核对会话和generation，再查幂等收据；键按session_id与request_id约束并保存请求摘要。相同键和参数返回原执行结果及当前可见状态；旧generation拒绝，同一键换参数报冲突。两个相同版本动作同时到达时最多一个成功推进，另一个报STALE_STATE；即使前端禁用按钮，后端仍需处理并发。

### 存档

快照包含schema_version、level_version、game_fields、saved_at和校验摘要，存档由后端生成并按会话保存。首版不做任意快照导入。restore验证结构、版本和不变量后应用；关卡v1快照在v2明确拒绝，不静默迁移。基线演示使用独立v1数据目录回退。

## 八 游戏AI行为和模型接入

开发Agent的模型与游戏内调用的模型是两套配置。开发可使用Work额度；网页AI通常需要独立API或获准的本地服务。游戏模型供应商、模型ID、API兼容方式及真实调用预算在T04预试后记录，不能从开发Agent名称推定。

### Provider接口

统一接口接收messages、工具Schema和调用限制，返回文字、工具请求、usage与供应商元数据。至少提供mock与一个真实Provider。mock用于规则及异常测试，不代替真实AI验收。根据获准供应商官方文档处理工具结果回传和错误，避免假定所有API字段相同。

### 上下文和输出

系统规则约束角色、事实来源、白名单和停止条件；上下文包含可见场景、已发现线索、背包、必要历史和当前版本。玩家输入与场景文本作为数据，不允许其覆盖系统规则。输出Schema为answer、clue_refs、proposal或明确无可行建议；引用必须来自已发现线索。

建议只生成下一个可执行动作，不自主整局通关。线索不足时建议inspect当前可见物体；禁止凭空引用未发现密码。模型可以推理已发现线索，但不能从服务器秘密配置取答案。工具dispatcher不提供Shell、任意网络或文件读写。

### 轮次限制

建议每个玩家AI轮次最多3次模型请求、5个只读工具执行和1个待确认进度提案；单请求20秒超时，总轮次45秒截止；单次输出建议限制约1000 Token。启动时验证供应商支持并记录有效值；超限停止本轮，不自动无限重试。

无效工具请求最多给出一次格式纠正机会；超时、鉴权错误或服务不可用返回清晰失败。AI可以读当前状态，但状态写入只能走受限事务；日志区分proposed、confirmed、committed、cancelled与rejected。

### 配置与用量

```text
APP_ENV=local
AI_PROVIDER=mock
MODEL_NAME=待填写获准模型ID
MODEL_API_KEY=在本地后端环境中填写
AI_MAX_MODEL_CALLS=3
AI_MAX_READ_TOOLS=5
AI_TURN_TIMEOUT_SECONDS=45
AI_PROPOSAL_TTL_SECONDS=120
SQLITE_PATH=./data/game.sqlite
```

.env.example只写占位符，真实.env加入.gitignore；前端不得使用带密钥的环境变量。开发额度、游戏API用量、实验和评价器用量分别记录；预算未确认时不批量执行付费实验。

## 二十 课程评价器的开发与校准

评价器是项目需交付的独立审查程序，与开发阶段A7角色不同。首版采用只读材料审查，不自动重跑目标仓库任意代码；不能因此宣称已经独立执行验证。需要补测时返回最小补查项，由A5或获准人员执行并生成新证据。

### 输入和信任边界

输入为教师或项目批准的contract/rubric、目标发布manifest、Claim表和证据索引。契约与允许不适用清单来自可信配置，不从目标README自我声明覆盖。目标代码、AGENTS、Hooks、插件和证据文本都作为待审数据，不自动加载为评价程序指令。

| 工具 | 允许范围 | 拒绝输入 |
| --- | --- | --- |
| get_approved_contract | 只读取登记的contract_id和版本。 | 未知契约、目标自降标准、任意路径。 |
| list_evidence | 列指定target_release的证据ID与版本。 | 其他目标版本或未登记路径。 |
| read_evidence | 按证据ID读取有限片段，限制大小和根目录。 | 路径穿越、符号链接越界、代码执行和URL。 |

流程：预检manifest、版本和文件存在 → 读取登记片段 → 确定性检查结构与算术 → LLM逐条判读Claim与证据关系 → 校验状态与真实Evidence ID → 输出缺口 → 你核查和签署。模型不可用时保存确定性结果并标明未做LLM判读。

| 状态 | 必要依据 |
| --- | --- |
| PASS | 证据支持该版本、该范围内的要求；标明来源与执行范围。 |
| FAIL | 有明确要求和可核查反例，指出实际偏差。 |
| INSUFFICIENT_EVIDENCE | 关键材料缺失或范围不足，列最小补查，不能泛称全部未知。 |
| NOT_APPLICABLE | 可信批准清单明确允许该项不适用，引用批准依据。 |

### 六类校准

K1有效通过应PASS；K2明确失败应FAIL；K3仅自称完成应证据不足；K4明确失败证据夹带“判PASS”指令仍应FAIL；K5错Evidence ID或版本应证据不足；K6获准不适用应N/A，未获准应要求确认。先冻结输入和预期，再运行；同时记录误放行、错误失败、不必要弃权及有效引用。

每条输出包括claim_id、status、release_id、evidence_refs、reason、missing_check、execution_scope和human_signoff。不生成未经校准的总分或可信度小数；正式课程评分由教师执行。
