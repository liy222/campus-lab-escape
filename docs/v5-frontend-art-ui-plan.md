## 2. 为什么这样构建

| 发现的问题 | 当前实现原因 | 本阶段处理方式 |
|---|---|---|
| 主题文字与画面脱节 | 已保存主题/故事，但背景仍由三个通用背景ID决定，物件只有少量通用图 | 增加独立主题包，在前端把已保存主题、公开房间/物件信息映射到对应美术 |
| 场景缺少整体感 | 生成场景使用八个固定槽位摆物件，HUD、物品栏和结算散落在页面上 | 统一场景构图与游戏外框，按同一布局安排画面、热点、物品栏和面板 |
| 物件身份不够可信 | 例如当前目录的`key`实际引用旧保险丝图片 | 给钥匙等实际角色补准确外形，统一场景图、物品栏、特写和完成状态 |
| 素材少、重复明显 | 多种资料共用同一纸张，设备缺少主题变化和公开状态表现 | 首包补三种空间、三类资料外观、六个物件角色及必要状态/特写 |
| 已有功能能运行，重写成本高 | 后端、生成、账号、存档和同步链路已存在 | 本阶段集中改呈现与资源选择，沿用现有API和规则 |

第一包是有限覆盖的主题资源库。玩家输入其他未覆盖主题时继续获得可玩关卡和真实主题文字，画面明确使用通用素材；本阶段不承诺任意描述都能实时生成专属图片。

## 3. 本阶段范围与完成结果

本阶段必须交付以下四项，作为一个完整功能阶段集中检查：

1. **完整的雨夜天文社主题包**：背景、物件、特写和必要状态能够在游戏中实际看到。
2. **主题到画面的接入链路**：匹配主题使用主题包；缺省或未支持主题保留通用表现；保存、重载和重新登录后选择一致。
3. **统一的新版 UI**：登录/创建/关卡列表与游戏画面风格一致，重点完善生成关卡内的场景、物品栏、谜题面板和结算。
4. **可复核的交付**：一次必要构建、受影响浏览器/数据检查、实际截图、简短复核报告和本人检查入口。

现有后端、AI提示/职责、生成结构、公开API、关卡定义、数据库和存档格式不在本阶段的改造范围。发现真实缺陷时，先说明关联和最小修复范围，不能借视觉改造替换这些系统。经典三房间页面保留原表现与功能。

## 4. 统一视觉与页面设计

### 4.1 美术方向

沿用用户此前接受的R1 v3柔和细节手绘方向，参考：

- [R1 v3样图](../output/art-concepts/r1-night-lab-v3-details.png)
- [原风格提示与边界](../output/art-concepts/r1-night-lab-v3-details-prompt.md)
- [已有手绘包说明](../output/art-concepts/SCENES.md)

表现：柔和水粉/铅笔质感，哑光材质，结构细节清楚，背景适度简化；旧木、暖纸、暗蓝雨夜和少量暖灯光形成层次。物件比背景更清楚，避免大面积单色空白、过密纹理和过暗到看不清的场景。

先在同一份设计说明中确定颜色、字号层级、间距、按钮、面板和状态样式。可以沿用现有森林绿/纸色基础，但场景氛围以天文社主题为主。登录、创建和游戏页面使用同一套设计规则。

### 4.2 页面结构

| 页面/状态 | 设计结果 |
|---|---|
| 注册/登录 | 清楚的游戏身份和进入入口，表单易读，忙碌/错误明确；保留已有验证与处理 |
| 创建/关卡列表 | 主题描述、房数、难度和生成状态清楚；主题包覆盖提示易理解；卡片能区分关卡与已有进度 |
| 生成关卡主画面 | 顶部紧凑标题/房间/常用入口，中间以场景为主体，物品栏和通道靠近场景；故事可展开，不挤占主要操作 |
| 物件特写 | 对应物件大图、真实名称/说明、已发现线索和可用操作形成明确顺序 |
| 线路/顺序/密码/终端 | 共用面板语言，各机制保留自己的清楚输入和状态，不改变既有解法 |
| 笔记/提示伙伴/存档 | 以侧栏或覆盖面板进入，读写状态与当前关卡一致，关闭后回到原位置 |
| 通关 | 在游戏框架内出现统一的结果层，显示真实统计，提供已有存档或返回关卡入口 |

桌面优先组织“场景＋紧凑操作区”；手机竖屏以场景和必要操作为首屏主体，长故事/笔记/存档在面板内滚动；手机横屏优先保留可操作空间。不要为了模仿桌面而把文字与点击区缩得过小。

## 5. 技术方案：独立主题包与前端视觉映射

### 5.1 接入位置和必须保留的旧接口

现有入口：

- `frontend/src/main.tsx`通过V5环境选择`frontend/src/v5/Workspace.tsx`；经典入口仍是`App.tsx`。
- `Workspace.tsx`已有`Level.theme/title/story`，继续把这些公开元数据传给生成关卡视图。
- `GeneratedPlay.tsx`管理游戏动作、面板、存档与同步，`GeneratedScene.tsx`负责Phaser画面与HTML热点。
- `CircuitBoard.tsx`已有真实线路呈现，继续使用。

**不要直接改写`frontend/src/assets/generated-catalog.json`的ID、version或含义。** 后端`backend/app/domain/generated.py`会读取它，关卡定义也使用其固定ID。主题图像另建前端包，在呈现时覆盖图片选择，服务端继续接收原object_id、target_id、item_id和动作参数。

新增建议位置：

```text
frontend/src/v5/visual/
  types.ts                         新主题包的前端类型
  resolveTheme.ts                  主题包选择与稳定物件映射
  ...                              必要的小型呈现组件/读取代码
frontend/src/assets/themes/rainy-astronomy/
  manifest.json                    独立资源描述，不替换旧生成目录
frontend/public/art-themes/rainy-astronomy/
  backgrounds/
  objects/
  closeups/
  ui/                              确有需要时使用
output/art-concepts/rainy-astronomy/
  ART-DIRECTION.md                  统一设计说明
  ASSET-LIST.md                     已制作/已接入/待补及来源
  prompts/                         实际使用的生图提示
  previews/                        实际样稿和联系表
```

一个主对话可统一修改这些路径。UI代码和素材放在不同目录是正常工程组织，不代表必须由不同对话执行。

### 5.2 主题与物件选择规则

1. 以**已保存的`level.theme`**作为主题选择依据；输入阶段可预告覆盖情况，正式游玩依据保存值选择。不要只依赖当前表单或浏览器临时状态。
2. 首包采用有限、确定性的天文语义匹配，如“天文社、天文、观星、望远镜”及明确英文同义。“观测记录”需有天文语境；仅有“雨夜、旧活动室、观测记录”不能自动判成天文主题。匹配不是新的模型语义服务，也不额外调用AI。
3. `neutral_lab`、`neutral_archive`、`neutral_control`只在前端分别映射为活动室、资料空间、观测设备空间；不改服务端背景ID、房间数或存档。
4. 物件首先依据公开的`art_id/kind/mechanism`选择兼容角色。不得按数组第几个物件猜测谜题，或为了主题把钥匙画成其他道具。
5. 同角色多份资料的外观由公开`level_id/object_id`等稳定标识确定；同一关卡重载保持一致。`slot`用于当前房间摆放，最多兼容现有0—7槽位。
6. `completed`等真实公开字段决定可用状态图。没有公开电源/门锁中间状态时，使用默认图；不在前端推导或虚构隐藏状态。
7. 若具体名称与主题专用外形不兼容，使用角色相符的中性外形，保留真实名称。不要为修补美术而重写AI名称、谜面或故事。
8. 缺少theme、角色或单张资源时，回到已存在的兼容素材，并能继续操作；主题包未覆盖的限制如实说明。

渲染适配只返回选用资源、布局和显示样式，不回写`definition_hash/revision/generation`，不保存到关卡定义或玩家数据库。图片路径来自本地目录，不接受模型给出的任意URL。

### 5.3 主题包描述约定

实现时在独立`manifest.json`中明确以下字段，并由类型/必要检查约束：

| 字段 | 内容 |
|---|---|
| `schema_version` | 新前端描述格式，首版为1，与旧生成目录版本独立 |
| `theme_id` / `pack_version` | `rainy-astronomy` / `1.0.0`，不因每次运行变化 |
| `display_name` | 雨夜天文社 |
| `backgrounds` | 按三个原背景ID映射本地图片，每张记录src、真实宽高 |
| `objects` | 按note/key/terminal/cabinet/circuit/panel分组，列出稳定变体ID |
| 单个变体 | 场景图、特写图、真实宽高、可见bbox、默认/完成状态引用及必要的空白文字区 |
| `slot_layout` | 1600×900逻辑画布上的八个位置、物件最大范围和热点区域，图与热点使用同一坐标来源 |

每个引用必须指向真实文件；bbox来自实际图像，不把整张透明画布当物件有效区域。新接口只在前端消费，不能为了省事扩展旧后端素材枚举。

## 6. 首包素材覆盖清单

### 6.1 三个空间

| 原背景角色 | 主题画面 | 必须可见的特征 |
|---|---|---|
| neutral_lab | 天文社旧活动室 | 雨夜窗景、社团使用痕迹、观测相关陈设及放置可交互物件的空间 |
| neutral_archive | 封存观测资料空间 | 同一建筑与画风，资料整理/保存氛围，避免直接画出正式线索内容 |
| neutral_control | 观测设备空间 | 天文设备与控制台氛围，保持当前机制可用；不新增真实望远镜操作玩法 |

三个背景支持1—3房间现有组合，不要求玩家必须经过三房才能看到主题特征。背景中的装饰望远镜/星图不自动成为新增交互任务。

### 6.2 六个现有物件角色

| 角色 | 本轮基础外观 | 需覆盖的可见变化 |
|---|---|---|
| note | 观测记录册、星图资料页、封存便笺三种兼容纸面外观 | 正式内容留空，由已发现公开线索叠加；无法兼容专门星图名称时选中性资料页 |
| key | 可识别的普通金属/黄铜钥匙 | 场景、携带图标、特写使用同一身份；收取后由真实对象列表决定是否消失 |
| terminal | 天文社资料/观测终端外形 | 默认与已完成，两态依实际公开completed |
| cabinet | 资料储物柜外形 | 默认与已完成；不推断不存在的中间开锁步骤 |
| circuit | 配电/连接设备外形 | 默认与已完成，实际线路仍由原小游戏数据呈现 |
| panel | 观测设备顺序面板外形 | 默认与已完成，符号与设备顺序由现有公开数据呈现 |

覆盖量为三张背景、八种基础物件外观与四类设备完成变化，即至少12种物件/状态呈现；八种基础外观都要有可读的特写表现。可复用同源高分辨率图、分层或共用框架，不要求为凑文件数重复生图。接入覆盖比磁盘图片总数更重要。

### 6.3 制作与接入要求

- 场景统一16:9构图，目标显示画布1600×900；背景建议不低于1600×900，资源描述写真实尺寸。
- 独立物件优先透明背景，保证边缘、比例和视觉中心；特写在实际面板中清楚，避免使用放大的低清缩略图。
- 场景和特写保持同一物件造型。背景预留物件位置，避免底图与叠加物件重复出现两个钥匙/柜子或产生不对应的热点。
- 密码、账号、线路方向、设备符号、排序和记录数值使用程序绘制的正式数据。生图文字、图形数量和装饰标记不能充当答案。
- 优先已有素材复用和内置图像工具，实际生图/编辑前读取当前可用的imagegen技能。不得使用项目DeepSeek Key或新增外部计费API来制作图片。
- 建议单背景交付大小不超过2MiB、首包不超过25MiB；这是资源优化目标，超出需说明影响。按主题/房间加载，先保证画质与可用，不为压缩破坏线索识别。
- 保存实际提示、源文件与接入清单；样稿和已经接入的图分别标注。集中看一张联系表与关键实际场景，无需每张图都暂停等待用户确认。

## 7. 任务顺序、归属与完成条件
